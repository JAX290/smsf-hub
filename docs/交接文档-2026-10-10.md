## 2. 系统全景（数据是怎么流的）

```
┌─ 手机端 APK（包名 cn.ppps.forwarder，显示名 Radio）
│
│  ① 短信 / 来电 / 已发送 / 定位  ──────────────→ 各自的通道，立即发
│  ② 命中「立即关键词」（验证码/扣款/登录…）────→ 立即发
│  ③ 系统应用（uid<10000）发的常驻通知 ─────────→ 直接丢弃，不上报
│  ④ 其余通知 ──→ 先进本地 Digest 表（带 due_at）
│                     │ 到点（默认普通 15 分钟 / 系统状态 24 小时）
│                     ↓
│          DigestWorker 合并成一个 POST：
│            DIG|N  +  N 行 JSON（每条一个消息）
│            ⚠️ 必须按序列化后的真实大小切包，见坑 9
│                     ↓
│          交给 SendWorker（复用离线队列的重试能力）
│
└─→ smsf-hub（VPS 上的 FastAPI，systemd 服务 smsf-hub）
       ├─ parse_digest() 把摘要包**拆回 N 条**，各自走正常流程
       ├─ 去重（设备+内容+时间的指纹）
       ├─ 分级 classify T0~T4（降噪核心，规则可在面板改）
       ├─ 归档 archive → Markdown 文件树，**永不自动删除**
       ├─ 推送 channels（低于 min_push_tier 的只归档不推送）
       ├─ 心跳 devices（面板按绿/黄/红显示每台手机）
       └─ 面板 panel：消息流 / 分析监控 / 归档搜索 / 手机管理 / 参数设置 / 自测
```

**关键设计原则（后面很多决定都是从它推出来的）**

> **手机是「中转站」，服务器才是永久档案。**
> 所以手机端可以激进裁剪（省空间、少隐私暴露），服务端一条不删。

## 3. 版本史：v50 → v71 都做了什么

> 版本号换算：`versionCode = v号 + 21`；装到机器上还带 ABI 前缀
> （arm64 是 `3*100000 + code`，例：v71 → code 92 → 装上去是 **300092**）

| 版本 | 内容 |
|---|---|
| v51 | 关掉 Cactus 的"无声音乐"保活（实测红米 18 小时音频唤醒锁占 96%、耗电全机第一）|
| v52 | App 名 → `Radio`、换收音机图标（`make_icon.py` / `make_glyph.py`）|
| v53 | 通知正文末尾追加属性行 `NAT\|cat=..\|ong=..\|imp=..\|grp=..`；跳过系统应用发的纯状态通知 |
| v54 | 修 `imp=`（渠道重要度）上报：必须用 `NotificationListenerService.getNotificationChannels(pkg, UserHandle)`（**复数**且要 UserHandle）|
| v55 | **攒批发送**：新增 `Digest` 表（数据库 25→26）+ `DigestWorker`；心跳响应接收服务端下发的窗口配置 |
| v56 | 修「攒批没合并」：新消息复用同一批的 `dueAt`（否则相差几秒的消息各自成批）|
| v57 | 修类型别名：手机端内部叫 `app`、服务端叫 `notify`，不转会落到默认 `sms`（每条通知都被当成短信）|
| v58 | **修「僵尸记录」**：`Logs.forward_status` 默认值是 1，凡是"插了行但任务没跑完"的永久停在 1、而重试只捞 0 → 消息永久丢失（实测卡住 3440 条跨 8 天）。修法：`status=1` 且已过 10 分钟也算待发；`MAX_PER_RUN` 200→500；心跳上报电池优化白名单状态 |
| v59/v60 | 按**内容**拦掉 MIUI「XX 正在后台运行」提示（实测这一条占某台手机全部消息的 23%）；修摘要 worker 被「取消重排」饿死 |
| v61/v62 | **数据精简**：`forward_response` 不再存请求体（68MB→0）、保留 2 天/3000 条封顶、删够量时 VACUUM；顺带**禁掉友盟统计**。实测数据库 **75.8MB → 5.11MB** |
| v63/v64 | **定位改为只读系统缓存**（不再注册 PASSIVE 请求）→ 系统的「正在定位」提示不再常亮；位移阈值不再频繁调地理编码 |
| v65 | **息屏 + 在移动 → 每 10 分钟自主定位一次**（保精度），平时只读缓存（保隐私）；地理编码复用阈值 100 米 → **10 米** |
| v66 | 「身体活动」权限改由 **App 自己申请**（首次运行问一次 + 挂在定位开关上），不再依赖 adb 预授权 |
| v67 | **版本名带标签**（`3.5.0.261010.v71`），系统「应用信息」/ App 内 / 面板三处都能看出是哪个包；服务端从心跳反推老包的 `v号` |
| v68 | 修 **MIUI 上「忽略电池优化」入口是死路**（标准 intent 被 MIUI 拦到自家「电量详情」页，那页没开关）|
| v69 | 「功能7」改成**两个并排开关** + **授权后锁死不能关闭** |
| v70/v71 | 修**摘要包撞上 WorkManager 10KB 上限**（导致手机端 2656 条消息卡住发不出去）+ 常驻系统通知的过滤放宽 |

**服务端同期改动**

- `app/classify.py`：T0~T4 分级（含 NAT 属性解析、关键关键词优先级修正）
- `app/analysis.py`：每日摘要 / 关键词监控 / 异常检测（含「手机端上报积压」）
- `/panel/search`：归档全文搜索（不受消息流窗口限制）
- `parse_digest()` / 摘要包拆分；`digest_config()` 随心跳下发窗口配置
- `devices.py`：设备状态 + **电池优化白名单**检查 + **版本标签**反推
- 归档永不自动删；磁盘不足提示下载

## 4. 手机端数据都存了什么（隐私 / 空间）

**v61 之前：没有任何上限，只增不减** —— 实测小米14 装 8 天涨到 **75.8 MB**，
其中 `Logs` 表 68.1MB（因为每条消息的正文被当成 HTTP 请求体又存了一份明文）。

现在是：

| 措施 | 默认 | 说明 |
|---|---|---|
| 不存正文 | 永远 | 拦截器丢弃 `body:` 行；响应文本截断到 500 字 |
| 保留天数 | 2 天 | 只删 `forward_status = 2`（已成功发出）的 |
| 条数上限 | 3000 | 已成功的 Logs / 无引用的 Msg |
| VACUUM | 删 >300 条时，一天最多一次 | SQLite 删行**不会**缩小文件 |
| 攒批队列兜底 | 30 天 | 正常情况下几分钟就发走了 |

**⚠️ 绝不碰待发(0) / 卡住(1) 的记录**（那些还要重试，删了就真丢）；Msg 也只删
「已经没有任何转发记录」的。

**顺带禁掉的第三方遥测**：`UMengInit` 原来在 release 包里会初始化友盟统计
（设备信息 + 页面埋点上报第三方），实测那台手机 `files/` 里留下了 `.umeng/`、
`um_ncc_local_config`、`umeng_it.cache`、`exid.dat`。v62 起改成空实现，debug/release 都不初始化。

**精简不掉的**：转发用的 `secret` 和配对钥匙必须留在手机上（否则功能就没了）——
它们是密钥不是内容。

## 5. 九个必须记住的坑 ⭐（最值钱的部分）

### 1. nginx 限流会把上报打成 503

```
/etc/nginx/conf.d/smsf-hook-ratelimit.conf:  limit_req_zone ... zone=smsf_hook:10m rate=5r/s;
/etc/nginx/sites-available/stratum-public-status:  limit_req zone=smsf_hook burst=10 nodelay;
```
手机上报一快就被拒，手机端日志是 `ApiException: Service Temporarily Unavailable`，
服务端 nginx 错误日志是 `limiting requests, excess: ... by zone "smsf_hook"`。
而且**三台手机经中转后 client 都是 127.0.0.1，共用同一个每秒 5 次的桶**，互相挤。
已于 2026-10-08 改成 `rate=50r/s` + `burst=200`（备份 `*.bak-20261008-145111`）。

排查口诀：**手机上报延迟高 → 先看手机日志里的响应码，再看
`/var/log/nginx/smsf-notic.error.log` 有没有 `limiting requests`。**

### 2. 「僵尸记录」：`forward_status = 1` 的消息永远发不出去

`Logs.forward_status` **默认值是 1**（不是 0）。新建行是 1，只有回调才改成 2（成功）或 0（待重试）。
任何「插入了行但请求没跑完」的情况（进程被杀、请求挂死、WorkManager 没调度、配对回调没回来）
都会留下一条**永远停在 1** 的记录 —— 而旧的重试查询只捞 `forward_status = 0`，消息就永久丢了。
（v58 修：`forward_status = 0 OR (forward_status = 1 AND time < now - 10 分钟)`）

### 3. MIUI「XX 正在后台运行」提示：一条通知占 23% 的消息量

`点按即可了解详情或停止应用。` 实测 8 天出现 9428 次；`睡眠服务后台运行中` 3237 次。
它是用 `com.android.mms` 的系统 uid 发出来的，**既不是常驻、也没有通知类别**，
靠属性判据拦不住 → 按**内容**拦（v59/v60）。

### 4. 拉手机数据库必须连 WAL 一起拉

Room 开了 WAL，`adb exec-out run-as ... cat databases/sms_forwarder.db`
拿到的是**没回写主库的旧数据**（表现为"队列明明是空的、Msg 数不动"）。
正确做法：把 `sms_forwarder.db`、`-wal`、`-shm` **三个文件拉到同一个目录**再用 sqlite 打开。

### 5. 摘要 worker 会被「取消重排」饿死

`DigestWorker.scheduleAtNextDue()` 每来一条通知都会调用。无条件
`enqueueUniqueWork(..., REPLACE, ...)` 会把"已经排好、马上就要跑"的任务取消再重排，
通知一多就一直在取消重排，worker 永远轮不到执行（实测队列堆到 20 条、最早一条过期 30 分钟）。
**正解：记住当前排着的到期时刻，只在新的到期时间更早时才重排。**
（中间试过 `KEEP`，但那会让"24 小时那档已排"挡住"15 分钟那档"）

### 6. MIUI 会把 App 的后台作业「冻结」——而所有标准检查都查不出来

`adb shell dumpsys jobscheduler | grep cn.ppps.forwarder` 会看到几十条
`Frozen status ... SystemJobService`。**同时**这些全是正常的：
电池优化白名单 ✅、`am get-standby-bucket` = ACTIVE ✅、`RUN_ANY_IN_BACKGROUND` = allow ✅、通知使用权 ✅。

这才是「消息延迟几小时」「夜里 7 小时零心跳」的真正原因，而且会自我强化：
上报积压 → App 长时间高 CPU → MIUI 判定异常 → 冻结作业 → 更发不出去。
后果之一是 WorkManager 里堆了 9871 个 ENQUEUED 永不执行的作业（`workdb` 涨到 61MB）。

**处理**：
1. 设置 → 应用设置 → 应用管理 → 收音机 → **省电策略 → 无限制**（⚠️ 和"电池优化白名单"不是同一个开关）+ **自启动**
2. 清僵尸作业：`am force-stop` 后删 `no_backup/androidx.work.workdb*`（消息在 Logs 表里，不会丢）
3. `am unfreeze` 只能解进程，**解不掉被冻的作业**

### 7. PASSIVE 定位照样会让系统一直亮「正在使用定位」

原来为了让 App「不主动定位、只蹭其他 App 的定位」，用 `PASSIVE_PROVIDER` 注册 —— 注释里
还写着"Google 文档明确：以 PASSIVE_PROVIDER 注册的 App 不算主动使用定位"。**这是错的**：
PASSIVE 只是不主动**发起**，它仍是常驻请求、App 仍在**接收**定位数据 →
Android 12+/MIUI 照样把「收音机正在定位」一直亮着（实测挂了 8h14m、locations=4997），
再叠加反复注册/注销的抖动，图标一直在闪。

**v63 修法**：干脆不注册请求，改成定时 `getLastKnownLocation()` 读系统缓存
（别人本来就在频繁定位：GMS 的 BALANCED、小米 fused、aicr 的 PASSIVE 一直挂着）。
验证方法：活跃请求列表里 `grep '^\s+[0-9]+/cn.ppps.forwarder.*Request\['` 应为空。

### 8. MIUI 上「忽略电池优化」的标准入口是废的

| intent | MIUI 上实际落在 |
|---|---|
| `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS`（原来用的）| `ResolverActivity` → MIUI「电量详情」页（**没有开关** ✗）|
| `IGNORE_BATTERY_OPTIMIZATION_SETTINGS` | `com.miui.powerkeeper...HiddenAppsContainerManagementActivity` ✓ 省电策略页 |
| `APPLICATION_DETAILS_SETTINGS` | `InstalledAppDetails` ✓（应用信息里也有省电策略）|

v68/v69：判断到 MIUI 就并排给**两个开关**（各跳一个入口），**授权后锁死不能关**
（关了夜里会被系统切断网络）。

**为什么非要设**：这开关**不在运行时权限里**，App 只能引导用户去系统设置点；
没设的话手机夜间深度休眠会切断网络，心跳和上报全失败、消息攒到早上才补发。
⚠️ 另外注意：**必要权限全都就位后，App 会把设置页换成绿色对勾**（当初要求"只要一个绿勾"），
想再进去看/改开关要**长按那个绿勾**临时解锁。

### 9. 摘要包会撞上 WorkManager 的 10KB 上限（整批发不出去）

`WorkManager.setInputData()` 的 Data **有 10240 字节硬上限**，超了不是截断、是直接抛
`Data cannot occupy more than 10240 bytes when serialized`，而且异常在**入队时**发生，
整批一条都发不出去 → 队列越堆越多（实测 2656 条、1152 条早已到期，用户侧表现是"消息不出来了"）。

**修法要分两步（第一版我修错了）**：
1. v70 按「正文字节数 ≤ 8000」切 —— **不够**：正文塞进 `Gson().toJson()` 会再做一次
   JSON 转义（引号/换行/非 ASCII 都膨胀），8000 字节的正文序列化后超过 10240 ✗
2. v71 **量序列化后的真实大小**（`Gson().toJson(msg).toByteArray().size`），
   边加边量、超过 9000 就切一包 ✓

顺带：`isSystemStatusNoise()` 原来要求「常驻 **且** 有类别」，但真机上最烦的常驻通知
**根本没类别**（`已连接到 USB 调试` / `正在通过 USB 充电` / `扫描设备` / `0B/s↑ 0B/s↓` /
`正在同步天气`）—— 2656 条积压里 1410 条就是它们。v70 起改成**系统应用的常驻通知一律不发**。

### 附：几个通用的踩坑

- **PowerShell 的 `Set-Content` 会把 UTF-8 中文写成 GBK** —— `versions.gradle` 和一份 README
  都被写坏过（靠 git 里干净版本还原）。改这类文件一律用编辑器。
- **`pwsh` 里内联 Python 极容易被引号搞崩** → 一律写成 `q*.sh` 再用
  `remote.py --stdin "bash -s"` 喂过去。
- **运行脚本结尾写 `exit 0`**，否则最后一条判断为假会让整体返回非零、被当成"运行失败"。
- **在 `pwsh` 里 `>` 重定向二进制会损坏文件**（adb 拉库、截图）→ 用 `cmd /c "... > file"`。

## 7. 操作手册（照着做就行）

### 7.1 改手机端 → 编译 → 装机 → **发布**（第五步最容易漏 ⭐）

```powershell
# 1) 改镜像里的源码（工作区内，不需要授权）
#    ...\radio\src\SmsForwarder\app\src\main\kotlin\...

# 2) 改版本号（⚠️ 用编辑器改，别用 Set-Content，会把中文注释写成 GBK）
#    ...\radio\src\SmsForwarder\versions.gradle
#      build_versions.version_code  = <v号 + 21>
#      build_versions.version_label = "v71"

# 3) 编译（要一次提权，产物在 C:\AndroidDev\...\build\app\outputs\apk\debug\）
Get-Process java -EA SilentlyContinue | Stop-Process -Force
Remove-Item -Recurse -Force "C:\AndroidDev\SmsForwarder\build\app\intermediates\merged-not-compiled-resources" -EA SilentlyContinue
cmd /c C:\Users\小米\Documents\deepseek-harness\radio\sync_build.bat
Get-Content C:\AndroidDev\build_last.log | Select-String "BUILD SUCCESSFUL|BUILD FAILED|^e: "

# 4) 装到手机（先确认是哪台！）
adb devices -l
adb -s <serial> install -r "C:\AndroidDev\...\Radio_v71_..._arm64-v8a_debug.apk"

# 5) ⭐ 发布到下载页（不做这步，用户下载到的还是旧版）
$env:SMSF_PASS="..."; $env:SMSF_HOST="<服务器>"
py -3 publish_apk.py        # 自动取最新一批 → 备份旧的 → 上传 → 逐个核对 md5
```

> **2026-10-09 的教训**：连着做了 v51→v71 十几个包，一个都没发布到下载地址，
> 页面上挂的还是 09-29 的 v49/v50 ✗。**「发布」要当成流程的最后一步。**

### 7.2 改服务端 → 部署

```powershell
# 1) 改 ...\radio\src\smsf-hub\app\... 里的文件
# 2) 部署（备份 → SFTP 上传 → 服务器 py_compile 自检 → 重启 → 面板页面自检）
```

### 7.4 排查手机（最常用的四条）

```powershell
# ① 看 App 自己的日志（MIUI 也能看！）
adb -s <serial> shell "logcat -b all -d | grep -iE 'NotificationService|DigestWorker|XHttp|OfflineRetry' | tail -30"
#    XHttp 那几行会打印请求 URL 和响应码，判断 503/401 一目了然

# ② 拉数据库（**必须连 WAL**）
cmd /c "adb -s <serial> exec-out run-as cn.ppps.forwarder cat databases/sms_forwarder.db > x.db"
cmd /c "adb -s <serial> exec-out run-as cn.ppps.forwarder cat databases/sms_forwarder.db-wal > x.db-wal"
cmd /c "adb -s <serial> exec-out run-as cn.ppps.forwarder cat databases/sms_forwarder.db-shm > x.db-shm"
#    然后 sqlite 打开 x.db，重点看：Logs 按 forward_status 分组、Digest 条数

# ③ 后台限制相关（三个都要看，缺一不可）
adb -s <serial> shell "dumpsys deviceidle whitelist | grep ppps"        # 电池优化白名单
adb -s <serial> shell "cmd appops get cn.ppps.forwarder RUN_ANY_IN_BACKGROUND"
adb -s <serial> shell "dumpsys jobscheduler | grep -c 'Frozen status uid'"  # MIUI 冻结作业数

# ④ 定位请求有没有挂着
adb -s <serial> shell "dumpsys location | grep -E '^\s+[0-9]+/cn.ppps.forwarder'"
```

## 9. 用户偏好与铁律

### 用户偏好

- **回复用简体中文**；每轮明确标 ✅已完成 / ⏳进行中 / ❌未完成
- 用户是**非技术用户**：改配置要能在**面板表单**里完成，或给一条能直接复制的命令
- **App 必须"隐蔽"**：不能自己弹界面、弹通知；桌面图标已移除（入口是快捷设置磁贴 / adb）
- **原始数据要一直保留**（服务端归档永不自动删）；存储不足时**提示下载**而不是自动清理
- 所有**真实通知**（真人消息、服务通知）都是重要的 —— 不要只硬编码微信/QQ
- 界面上**只要一个绿色对勾**，其它话都不说（就绪时锁定设置页，长按绿勾临时解锁）

### 铁律（都是踩过的）

1. **绝不给 `/etc/nginx/sites-enabled/` 加文件**；不动 `relay1.mulinsen.win`
2. `Preset.kt` 是 LF、`SettingsFragment.kt`/`MainActivity.kt` 是 CRLF（改完别搞混）
3. 只改项目目录，别动 VPS 上别的东西
4. 华为手机安装需要手动确认
5. `config.yaml` / `channels.yaml` **只存在于服务器**，不进仓库（含 secret）
6. 装 APK 前先 `adb devices -l` 确认机型
7. 验证 APK 内容用 UTF-8 字节匹配 / `aapt dump badging`，不要只看编译日志
